# 导入账单

## 操作顺序

1. 从本轮 `staged_import` 取 `stage_id`。没有附件 id 时用 `finance_import_read(mode=stages)` 看是否有明确对应的暂存；没有或无法确定时，请用户用页面表单选择文件。解压密码只填表单，不进对话、路径或工具参数。
2. `finance_import_read(mode=stage, stage_id=...)` 看平台、范围、有效行和解析失败等，需要明细时用 `next_offset`。用户只要求查看解析时到这里；不自行入库。
3. 用户明确要求导入该附件就 `finance_import_commit(stage_id=...)`。以 `state=committed` 和批次回执的 `inserted/skipped/failed` 核对结果。查过去的入库用 `mode=batches`。同一个 `stage_id` 已提交会拿回同一批次，不会再写一次。
4. 若还要求整理 V2，按回执里的 `batch_id` 查本次新增且尚未初始化的交易。例如在 SQL 用 `transactions_raw.id = agentcore_tx.tx_id` 关联，再筛 `transactions_raw.import_batch`。完成初始化、分类等要求，并通过账本工具读回。重复跳过的交易不会因此变成本批新增。

## 为什么

- **解析、入库、初始化是三种不同状态。** 解析只生成暂存；导入只增加凭证；初始化后才有 V2 归属与账本金额。混在一起会让用户以为已经入账，但 V2 查询找不到。
- **跳过与失败不同。** 判断最终写了几笔必须看持久回执，不能从解析行数或重复估算倒推。日期范围是被处理文件的覆盖，不是所有新增记录都覆盖这些日期的证明。
- **需要澄清的是输入，不是每步许可。** 压缩包无法解开，请在表单重新填密码；附件过期请重传；请求日期与附件明显不符时先问具体要哪个，不自行挑另一个文件。少数解析失败若不妨碍用户要求的导入，就如实报失败数和首错，不把部分成功说成全成功。

## 虚构示例

用户说「导入我刚传的账单，把新增的放到『六月试账』」。读暂存后提交，回执为新增 3、重复 1。用返回的批次号取新增的 3 个 id，按用户指定目标执行 V2 初始化；重读节点后报 3 笔入账和 1 笔重复跳过，不把重复的第 4 笔也算进这次初始化。
