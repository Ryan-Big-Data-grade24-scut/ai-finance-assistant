# 自动分类与参考历史

## 操作顺序

1. **查候选。** `finance_query_transactions` 按用户的选区、日期、批次、方向取候选，新增整理用 `initialized=0`。已初始化的只在用户要求调整时处理。大批任务先聚合看量，再用稳定 `ORDER BY` 分页，分页边界不要用写入过程中会减少的 `initialized=0` 集合加 OFFSET（会跳过未读行）；可先记明确 id，或按 id 续读。
2. **查目标和证据。** `finance_ledger_read` 的 `summary` 和 `node` 查当前树；`classification_examples` 查仍与实际目标一致的旧手工确认。关联历史交易的 `counterparty`、`item`、`direction`，对照本轮候选；用户指定的范例用 `tx` 读真实位置。旧手工确认可能为空，当前放置仍可作为参考，但标「当前归属」，不标「用户确认」。
3. **定规则。** 明确每组候选的目标 id 或要创建的节点、理由和证据。优先用户本轮指示，其次用户认可的同类记录；同商户还要看方向与商品语义。平台 `category` 只是人工覆盖或平台类别的流水字段，不是 V2 节点。冲突无法判定时只留这些交易待澄清；不要暂停已经明确的部分，除非用户要求整批一次决定。
4. **照目标执行并复核。** 用户要求的是建议就只给建议；明确要归类时，未初始化用 `init`: 单目标用 `target` / `new_node`，多个目标用 `plan.place`；已初始化独立主交易用 `move`。不要为了归类自动拆组、分裂或调整组员。用回执的实际 id 和 `finance_ledger_read` 重读，报已处理数量、证据和未处理项。几步以上用 `todo_write` 跟进。

## 为什么

- **不把自己的分类循环当作用户偏好。** 平台预设、当前账本、旧手工确认和本轮指定权重不同。如果把前一轮助手的推断标成确认，下一轮会放大原来的错。
- **不靠名字猜树。** 重名节点和净额组可能在不同位置；单笔移动也可能带动整组。用真实 id 绑定目标，有组员冲突时问用户意图，不能假装能只动一条腿。
- **不需要中间摆放。** 自定义初始化可以一次放到最终位置。先按平台全量初始化再移动，既扩大范围又让回滚分成两步。

## 虚构示例

用户说「照以前的习惯把新导进来的三笔分类」。同商户同方向的午饭与手工确认样本一致，归餐饮；地铁充值按商品语义归交通；另有一笔只有笼统名称且历史冲突，暂留未初始化。执行前两笔并核对，报告确实落账的两笔和剩下一笔需要什么信息。
