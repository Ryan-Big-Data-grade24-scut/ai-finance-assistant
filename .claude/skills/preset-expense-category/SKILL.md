# 预设支出分类

**先剔除非消费，剩下的按固定树和固定判据一次归到位。** 承接 `split-income-transfer-spend`：转账、存取、理财申赎、重复副本、退款已经分到各自分支，这里只处理**真实支出**。不要重新发明分类树——用下面这套预设；用户另有口径就按用户的，并说明改了哪一条。

## 预设分类树

- 真实收入
  - 收益·理财／零钱（余额宝、零钱通、理财通一类）
  - 收入·固定来源（工资、家庭代付、固定生活费，按用户口径命名）
  - 收入·额外转账与红包
- 账户搬运
  - 转入／转出（钱包↔银行卡↔理财账户↔小荷包）
  - 重复消费副本（同一笔消费在两个平台各留一条）
- 退款（挂回原消费所在的大类下面）
- 消费
  - 饮食：早餐 / 午餐 / 晚餐 / 零食
  - 交通：公共交通 / 单车 / 停车费 / 打车
  - 医疗
  - 住宿
  - 生活弹性支出：理发 / 文具 / 话费 / 其他零散
  - 工具订阅：按厂商分（AI 接口、VPN、服务器一类）
  - 其他（待确认）
- 其他（待确认）

节点不存在就用 `init` 的 `plan.nodes` 建，命名跟用户习惯走。

## 判别顺序（按顺序走，不要跳步）

1. **先剔除非消费。** 命中任一条就不计入消费：本人账户之间的转账或存取；理财、基金的申购赎回与转换；同一笔消费在两个平台各留一条的副本；退款或退回。剔掉的按上表进对应分支；转账还要建成净额组合并生成镜像，见 `split-income-transfer-spend`。剔不掉的不要硬塞。
2. **定大类。** 看**商品语义加商户类型**，不看平台的 `tx_type`——那只是平台自己的分类，食堂消费在平台里可能叫「教育培训」，按它归就会归错。正餐类商户、超市便利店、医疗机构、网约车与地铁、共享单车、酒店、话费充值、订阅服务，按商户类型落到对应消费分支。
3. **定小类。** 只有树里给了小类的分支才分小类：
   - **饮食**：正餐类商户按时间窗切——早餐 ≤11:00、午餐 11:00–16:00、晚餐 ≥16:00；超市、便利店、烘焙、茶饮、零食、水吧、自动售货机、外卖夜宵一律进**零食**，不看时间。同一商户既卖正餐又卖零食时（食堂里的超市、便利店的便当），按时间窗判正餐还是零食。
   - **交通**：公共交通（地铁、公交、一卡通充值）、单车（共享单车骑行）、停车费（停车、车位、月租）、打车（网约车、代驾）。加油、保养、洗车归养车一类，不塞进打车。
   - **工具订阅**：按厂商名分，一个厂商一个节点。
4. **判不准就进「其他（待确认）」。** 商户名是通用词、金额明显大、或两种归法都说得通时，留待确认并写清缺什么信息。**不强配**，也不把待确认整类加作消费。

## 批量落位

- 一次 `finance_ledger_apply(op="init", tx_ids=[...], plan={"nodes": [...], "place": [...]})` 把整批放到位，不要一笔一笔 `move`。
- `place` 里同一个节点写一次，列出该节点的所有 `tx_id`；没提到的交易会落到根下，先把名单凑齐再执行。
- 已经在 V2 的交易用 `move(items=[...], target=...)`；`move` 会带走整组成员，组员和目标冲突时先确认意图。
- 落完用 `finance_ledger_read(mode="summary")` 和 `mode="node"` 读回各分支的 e/i 与笔数，和上面的预设树对一遍；对不上先查漏放和错放，再报结果。

## 为什么

- **固定树才有可比。** 每次换一套分类，跨月的支出就没法比。预设树的价值在稳定，不在完美。
- **先剔非消费，再分类。** 顺序反了会把转账算成支出、把重复消费算两次，分类做得再细也是错的。
- **平台 tx_type 不可信。** 按商户语义判更稳，也更能跨平台对齐。
- **待确认比错配便宜。** 错配会静默改掉月度数字，待确认只是多问一句。

## 虚构示例

一批新流水里：一条本人银行卡转理财账户（转账，剔出消费）、一条便利店 15 元（零食）、一条食堂午餐 12 元（午餐）、一条共享单车 3 元（单车）、一条体检费 200 元（医疗）、一条只写「扫码支付」的 88 元（待确认）。落位后读回：饮食下只有午餐和零食，交通下只有单车，医疗下只有体检，待确认 1 笔并写明缺商户信息。
