# 第二轮 · 设计思路

> 这一轮不做智能，做基座。
> 本文只讲**为什么转向**和**大致要做成什么样**。

---

## 一、为什么转向

### 1.1 上一轮的设想

第一轮机械部分跑通后，想直接做智能：

```
用户的一句话 → 提问 → 统一口径 → 制作用户想要的账单 → 辅助决策
```

纸面上完整，工程上危险。因为它把四件性质完全不同的事捆在了一起：

| | 性质 | 坏掉时 |
|---|---|---|
| 提问 | 交互 | 用户烦了，不玩了 |
| 口径统一 | 语义 | 算出来的数不对 |
| 分类 | 判断 | 分类错 |
| 决策 | 生成 | 建议不中用 |

**任何一件不稳，整条链就不可用。** 更麻烦的是它们互相掩盖——分类错了会被"提问纠正"掉，口径错了会被"分类分散"掉。

结果就是：**分不清「系统出了 bug」和「用户还没被问清楚」。** 这是没法调试的。

### 1.2 改成什么

**先把能独立成立、独立验收的能力逐个做扎实，再谈组合。**

```
这一轮：                        以后：
  基座 A ──┐                      基座 A ──┐
           ├──→  组合  →  智能      基座 B ──┤
  基座 B ──┘                                    ├──→ 组合 → 智能
```

组合是有价值的，但**只有当每个基座都能独立跑、独立测、独立验收时，组合起来才有意义**。

### 1.3 判断标准变了

第一轮问「它能不能做对」。这一轮问：

> **「它坏掉的时候，会不会伤到别人？」**

因为基座是给别人用的。两个基座的性质不同，标准也就不同：

| | 基座 A：粗分类 | 基座 B：代数引擎 |
|---|---|---|
| 错一次的代价 | 用户改一笔 | 账目失真，用户不知情 |
| 验收标准 | **稳定**（同样输入给同样输出） | **精确**（算出来一定对） |
| 目标 | 80 分且不下滑 | 100 分 |

> **A 要「稳定地不完美」，B 要「精确地不犯错」。**
> 这两个标准不能混用——用 A 的标准要求 B，会漏掉真正的 bug。

## 二、我们放弃了什么

放弃的东西比保留的更能说明这轮成熟了。

**放弃「一步做出用户完全满意的账单」。** 「满意」没有可判定的标准，做出来也不知道离目标多远。基座是可验收的。

**放弃「让 AI 全权决定分类」。** 代数里 `Y = M(X)`，**记账方式是函数，不是事实**；同一个 X 在不同 M 下得到不同 Y，而且**都可能是对的**。所以 AI 分类只是**某个 M 的初值**，用户改它不是纠错，是换 M。这定位一确立，**AI 分类错 20% 就完全可接受**。

**放弃「先做功能再想架构」的反面——「先写完所有设计再动手」。** 上一轮我们花了很久把设计写全，结果代码一行没动。**这一轮的纪律是：文档跟着代码走，不领先于代码。**

---

## 三、两个基座

### 3.1 基座 A · AI 粗分类

给每一笔交易一个分类建议。

**明确不做什么**：不追求准确（80 分即可）、不追求解释、不做终局判定、不碰金额和时间这些事实字段。

**为什么它值得做**：代数里原子的展开只有退款合并、分裂、单腿三条路，**都是确定性规则，跟"这笔是什么"无关**。"这笔是餐饮还是交通"体现在**它被放进哪个节点**。

所以 AI 粗分类的价值不是"帮你分对"，而是：

> **让用户打开界面时，看到的不是一棵空树，而是一棵已经有大致形状的树。**

用户的工作从「从零归类一千笔」变成「微调已经对的地方 + 修正明显错的地方」。**这是 O(全部) 到 O(可疑部分) 的下降。**

**它必须稳定**——同样的输入必须给同样的输出，否则用户每次打开看到的形状都不一样，**心智模型建立不起来**。

> 这条直接推翻了"逐笔调大模型"的做法：逐笔调用时同样的输入同样输出也可能不同。

### 3.2 基座 B · 代数引擎 + 可视化

这是这一轮真正有难度的部分。

代数里最关键的一句：

> `Y = M(X)`，M 是一个函数。
> 讨论「这个月花了多少」时，**隐含地已经选定了 M**。

第一轮里，**用户完全接触不到 M**——口径硬编码在视图的 WHERE 和各个模块的映射里。用户改一个字段，数字就变，而且**他不知道变了什么、为什么变**。

**第一轮的用户以为自己在看事实，其实他在看一个函数的输出。** 这是最大的认知缺口。

基座 B 要做的，就是**把 M 变成一个用户能看见、能直接操作的对象**。

#### 大致长什么样

两种呈现方式，同一棵树的两个投影：

**顺序列表** —— 按时间平铺每一笔。适合逐笔核对。

**星图** —— 根节点在中心，向外逐层发散，最外层是每一笔具体交易。

```
                    一次 AA 聚餐（组）
                         │
        ┌────────────────┼────────────────┐
     正餐              零食            地铁
    ┌─┴─┐            ┌─┴─┐           ┌─┴─┐
    τ   τ            τ   τ           τ   τ
```

星图的价值**不是好看，是让"层级"这个抽象概念有了空间直觉**：

- **离中心的距离 = 归得多深** —— 一眼看出哪些分得细、哪些直接挂在总账下
- **扇形角度 = 占总账的比例** —— 大小关系不用读数字
- **节点上的一个标记 = 它是"直接相加"还是"内部相抵"**

而且它天然对应代数的两个结构：**内部节点带一个 op，叶子是一笔交易**。

#### 用户能在上面做什么

代数里的每个算子，**都对应一个用户能做出的具体动作**：

- 把几个节点并到一起
- 把一个节点改成"内部相抵"
- 把一笔拆成两半
- 把几笔从一处挪到另一处

**代数里的顺序敏感、适用域、幂等性这些抽象性质，在星图上变成了看得见的手势差异。**

这不是把数学可视化，是**用可视化承载数学**。

#### 后端的要求

用户的要求是：**前端不管怎么造，后端都不会出任何错误。**

这句话要翻译成可检验的工程要求：

> **后端只接受代数定义得合法的操作；非法组合要么被拒绝，要么被规范化成有定义的等价形式。绝不返回错误的结果。**

做法是**每次操作后自动校验代数里的不变量**，不通过就拒绝这次操作并说清原因。

还有一条容易被忽略但很重要：**口径要能版本化、能重跑**。否则用户改一个定义，上个月的账就再也算不出来——而"为什么这个月和上个月对不上"恰恰是最容易被问到的问题。

### 3.3 两个基座的关系

```
基座 A（粗分类）                基座 B（代数引擎 + 星图）
      │                                    │
      │  生成初始树                          │  承载所有后续操作
      ▼                                    ▼
  ┌──────────────────────────────────────────┐
  │        同一棵账本树                        │
  └──────────────────────────────────────────┘
```

A 负责**把树长出来**（省掉 O(全部) 的手工），B 负责**让树可以被安全地改造**（这才是记账本身）。

A 的产出直接是 B 的输入，所以 A 的粒度必须对齐 B 的层级：**粗分类只到"用途"这一层，一次 AA 聚餐那样的组不交给 AI** —— 那需要上下文，只有用户能划。

> **AI 只做能稳定做的事。** 这条边界是这一轮的底线。

## 四、做完之后，智能在哪

这一轮不做智能，但要说清楚**智能从哪来**，否则会担心走偏了。

代数里已经写好了完备性条件：

```
(T1) 完备     机器可判定
(T2) 一致     机器可判定
(T3) 目的达成 唯一机器无法判定的 —— 用户认为够细了
```

> **机器负责：报告客观状态（还剩多少笔没解释、断言是否通过）
> 人负责：判断够不够细**

**「智能」要做的事，在代数里已经被精确定位了** —— 它就是替人回答 (T3)，并把"哪些笔还没被解释"组织成有效的问题。

而这两个基座正是它的前置条件：

- 没有基座 A：智能面对的是**一棵空树**，提问无从谈起
- 没有基座 B：智能的每次改动都**可能破坏账目**，用户不敢让它动

> **所以转向不是放弃智能，是把智能的地基从「一堆功能」换成了「一个数学地基 + 两个可靠基座」。**

## 五、这一轮大致做成什么样

| | 大致样子 |
|---|---|
| 基座 A | 一批交易跑完，产出一棵有形状的树。**跑三次结果一样。** |
| 基座 B | 星图能打开、能改；改完数字对；前端乱造也不会算出错账 |
| 两者接上 | 粗分类的产出**就是**树的初始形状 |

第一轮那 5 轮 onboarding 的真实数据还在（`Temp/md/20261015_ai-finance-impl/onboarding/round1~5/`），用户逐笔确认过的分类**就是现成的评测集**，数字对不对**有基线可比**，不用另外造数据。

## 六、架构：后端 → 引擎 → 前端 / 暴露给 AI 的插件

### 6.1 分层

```
┌──────────────────────────────────────────────────────┐
│  后端  FastAPI                                        │
│  · 导入 / 去重 / 原始事实（不可变）                       │
│  · 报告查询                                             │
└──────────────────────┬───────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────┐
│  记账代数引擎  ★ 唯一真相源                            │
│  · 账本树：节点 / op / 归位                            │
│  · 算子：聚合、净额、拆分                               │
│  · 不变量校验 —— 非法操作在这里被拒绝                    │
│  · 口径快照：可重跑、可对比                             │
└───────┬──────────────────────────────┬───────────────┘
        │                              │
┌───────▼──────────────┐   ┌───────────▼───────────────┐
│  前端  Vue            │   │  暴露给 AI 的插件           │
│  · 星图 / 列表        │   │  · Hook：每轮注入状态         │
│  · 用户直接改树        │   │  · MCP：取明细 / 提交分类      │
│  · 改完立刻看到数字     │   │  · AI 分类 → 过引擎 → 落账   │
└──────────────────────┘   └───────────────────────────┘
```

**引擎在中间，前端和插件是它的两个对称的客户端。**

- 前端：人操作，视觉反馈是星图
- 插件：AI 操作，视觉反馈是结构化 JSON

两者走**同一套引擎接口**，走**同一套校验**。所以 AI 做的任何事，前端都能看见；前端能做的任何事，AI 也能做。

### 6.2 为什么引擎必须是唯一的分叉点

```
前端 ──┐
       ├──→ 引擎 ──→ 落账
插件 ──┘
```

**如果前端和插件各写各的落库逻辑，就会出现两个真相。** 第一轮已经踩过这个坑的雏形：`v_tx_counted` 里硬编码的 `WHERE is_exempt = 0` 就是一个绕过统一口径的第二套逻辑。

所以：

> **「后端不会出任何错误」这句话，是引擎的职责，不是前端或插件的。**
> 前端乱造、插件乱填，最后都汇到同一个校验口。

### 6.3 插件这一侧

插件是引擎的**第三个客户端**（前两个是前端和 MCP 工具本身）。它的特殊性在于**操作者是 AI**：

| | 前端 | 插件 |
|---|---|---|
| 谁操作 | 人 | AI |
| 输入 | 拖拽、双击 | 结构化 JSON |
| 失败表现 | 界面抖动 + 一句人话 | 逐笔拒绝 + 理由 |
| 上下文来源 | 用户的眼睛 | 用户 harness 的历史 |

插件不建节点、不改 op、不碰事实字段——**它只做归位**。详见 `01_AI分类插件.md`。

### 6.4 一句话

> **引擎是账本，前端和插件是它的手。**
> 手可以有很多种，账只有一本。
