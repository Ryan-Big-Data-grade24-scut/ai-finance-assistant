# 第二轮 · AI 分类插件

> 一个必须外接用户 harness（Claude Code / MCode）才能用的插件。
> 它引导用户的 AI 主动去读每一笔交易的细节并分类，产出**结构化结果**，
> 由记账代数引擎落账——**不直接写数据库**。

---

## 一、它是什么

一句话：

> **一个把「用户的 AI」变成「分类器」的插件。** AI 读交易明细 → 按约定格式输出分类 → 引擎校验并落账。

它**不是**一个后台跑批的模型服务。分类这件事由**用户的 AI** 干，用用户自己的 harness、自己的模型、自己的上下文。插件只负责三件事：

1. **告诉 AI 现在该干什么**（推什么、什么格式）
2. **校验 AI 的输出**（格式对不对、合不合法）
3. **把结果交给引擎**（而不是直接写库）

---

## 二、为什么是插件，而不是一个 API

### 2.1 分类的原料就是上下文

一笔交易要判对，AI 需要知道的东西远超这一行：

```
2026-09-22 16:01:30  支出 59.26  暨南大学附属第一医院（商户2）  门诊缴费
```

光看这一行，AI 判不出「25 挂号 + 30 检查 + 4.26 右佐匹克隆」。它需要：

- **同一时间附近的其它交易**（那 59.26 之前有一笔 25 的挂号）
- **历史同类**（这个医院每月都来一次）
- **平台原始分类**（支付宝一会儿归「医疗健康」一会儿归「美容美发」）

**这些上下文，只有用户的 AI 手里有**——它知道用户之前说过什么、知道这个项目的历史。

一个后台分类服务拿不到这些，除非它自己再建一套上下文系统。**那就成了另一个产品。**

### 2.2 用用户自己的 harness，代价为零

用户已经在用 Claude Code / MCode 了。用它的模型、它的额度、它的上下文：

- 不花钱（用户的订阅内）
- 不需要 API key
- **AI 已经在项目里，知道账本长什么样** —— 第一轮那 5 轮 onboarding 的对话历史就是最好的 few-shot

### 2.3 而且这本来就是"智能"的一部分

我们之前把「智能」定义为「问用户 → 统一口径 → 决策」。但**分类也是智能**。

如果 AI 分类走 API 服务，那它和用户的 AI 是**两个大脑**，两边的判断会打架：
- 后台分类说「餐饮」，用户的 AI 说「零食」，谁的算？

走插件，**只有一个大脑**。这是比"准确率"重要得多的理由。

## 三、它长什么样

### 3.1 形态：MCode Plugin / Claude Code Hook

沿用已有的调研结论（`Temp/.../model/01-Hook机制调研.md`）：

```
.minimax-plugin/plugin.json      → 声明 hooks
hooks/hooks.json                 → 事件绑定
scripts/classify-hook.mjs        → 注入提示词 + 校验输出
```

**Hook 事件选 `UserPromptSubmit`** —— 每轮注入，模型处理前触发。

```
用户："帮我把这个月的账分类一下"
        ↓
UserPromptSubmit hook
        ↓  读引擎状态 → 算出"还有哪几笔没分类"
        ↓  注入 additionalContext
模型：看到指令 → 调 MCP 工具取那批交易的明细 → 看 → 输出格式化的分类结果
        ↓
模型：调 MCP 工具 submit_classifications(...)
        ↓  引擎校验 → 落账 → 返回"已入账 37 笔，2 笔被拒（理由）"
```

### 3.2 为什么 hook 和 MCP 要配合

单靠 hook 不行：hook 只能**注入文本**，不能做"取数据 → 给模型 → 收结果 → 写库"这个循环。

单靠 MCP 也不行：MCP 是 **client pull** 模型，服务端没法主动把提示词塞进上下文。调研里写得很清楚：

> **MCP 提供能力，不提供时机。要「强制」，必须用客户端的 Hook。**

所以分工是：

| | 职责 |
|---|---|
| **Hook** | **什么时候说、说什么** —— 算好状态，注入状态摘要 |
| **MCP 工具** | **重活怎么干** —— 取明细、提交分类、查引擎状态 |

> ⭐ 关键技巧：**hook 注入的文本里直接写明该调哪个工具名**。这样模型的下一跳是确定的，不需要它自己猜。

### 3.3 hook 注入什么

按调研里的硬约束，**注入文本 ≤ 65,536 字符**，所以只能注入**状态摘要**，不能塞全量数据。

```
【账本 · 待分类】
区间 2026-09-30 ~ 2026-10-16　　粒度：大类 + 小类
待分类 37 笔　已分类 159 笔　低置信 5 笔

请调用 query_classification_batch(limit=40) 取待分类明细，
逐笔判断后调用 submit_classifications(...) 提交。
格式：{"tx_id": int, "category_l2": str, "category_l3": str, "confidence": float, "reason": str}
每笔必须有 reason；不确定的用 "不确定" 并把 confidence 压低。
```

**这个注入文本同时承担了提示词的角色** —— 格式要求、注意事项、边界都在里面。

## 四、⭐ 分类结果怎么落地：必须过引擎，不能直接写库

### 4.1 这是整个设计的关键约束

> AI 分类的产出**不是**"往 `transactions_raw` 或 `tx_overrides` 里写一行"。
> 它是**对账本树的一次修改**。

为什么：

- 代数里 `Y = M(X)`，**M 是函数不是事实**。「这笔是餐饮」这个判断，**只有在"餐饮"这个节点存在、且它的 op 确定时才有意义**
- 如果 AI 直接写 `manual_category`，那分类是**一个字符串**，不是**树里的一次归位**
- 那么「一次 AA 聚餐」这样的组怎么办？它是一组交易，**字符串装不下**
- 那么 NET 怎么办？一个 NET 节点里的交易，分类只是其中一半

**所以：分类 = 把 τ 放进某个节点（或新建节点）。这是树的操作。**

### 4.2 写入路径

```
AI 输出 JSON
    ↓
MCP 工具 submit_classifications
    ↓
  ① 格式校验（schema）
  ② 标签校验（category_l2 / l3 是否在词表内）
  ③ 引擎操作：把 τ 归位到对应节点
  ④ 引擎校验不变量
  ⑤ 通过 → 落账 + 返回新树状态
     不通过 → 拒绝 + 说明哪条不变量挂了
```

第 ④ 步是这一轮的核心承诺：**「后端不会出任何错误」在这里兑现。** AI 无论输出什么，账都不会算错——最坏是被拒绝。

### 4.3 ⚠️ 一个必须承认的张力

粗分类和树模型之间有一处**真实的矛盾**，我不藏：

**粗分类要的是"平铺、快、稳定 80 分"；树模型要的是"结构、精确、可编辑"。**

具体说：AI 判「这 37 笔都是餐饮」——在树模型里，这不是一个分类结果，而是**"建一个叫餐饮的节点，把 37 笔放进去"**。

这没问题。但如果 AI 判「餐饮里还分正餐和零食」，它就必须同时说"建两个子节点"——**这已经超出了"分类"的范畴，进入了"设计账本结构"**。

**两条路，选一条：**

| | 方案 A：AI 只填节点 | 方案 B：AI 也能提结构建议 |
|---|---|---|
| AI 输出 | `tx_id → 节点路径` | `tx_id → 节点路径` + `新节点建议` |
| 引擎动作 | 只归位，节点必须已存在 | 可以建节点，但**建了要用户确认** |
| 稳定性 | 高（节点是固定的） | 中（AI 可能今天建"正餐"明天建"正餐/午餐"） |
| 复杂度 | 低 | 高 |

**建议方案 A** —— 理由是稳定性。

节点树由**用户 + 引擎的既有结构**决定，AI 只负责"这笔去哪"。**节点的增删改是用户的事**（在星图上拖）。

> 这样分工之后，AI 分类的稳定性问题就退化成："同样一批交易，AI 会不会选到不同的节点？"
> 节点集合固定之后，这比"分类是否准确"好得多保证——**因为它是一个受约束的选择题，不是开放题。**
