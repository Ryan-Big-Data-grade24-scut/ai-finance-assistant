# 04 · 骨架与契约

> **这一份是「层与层之间怎么说话」的真相源。**
> 别的文档讲**要做什么**；这一份讲**谁只能做什么**。
>
> 判据只有一条：**改代码时，能不能只看这一份就知道该改哪儿、不能改哪儿。**
> 做不到的地方，就是骨架没建好。

---

## 一、一句话架构

```
HTTP (main.py)  ┐
                ├─→ service（唯一写路径）→ store（唯一写 ledger_* 的地方）→ SQLite
MCP  (server.py)┘         ↑
                          ops（纯函数）→ invariants（每次写后自检）
```

依赖方向单向无环：`schemas ← ledger ← (main, mcp)`。
账本层是**第四条平行通道**，不插进第一轮链路中间。

---

## 二、层与唯一入口

| 层 | 位置 | 唯一入口 | 允许写 | 禁止 |
|---|---|---|---|---|
| 原始层 | `backend/importer/` | `import_file` | `transactions_raw`, `import_batches` | UPDATE/DELETE raw |
| 修正层 | `backend/overrides.py` | `set_override` | `tx_overrides` | 碰 raw |
| **账本层** | `backend/ledger/` | `service.apply_op` / `undo` / `redo` / `reset_to_m0` | `ledger_*` | 碰 raw / 写 overrides / import `backend.reports` / 查 `v_tx_counted` |
| 读层 | `backend/reports/` | 7 个只读函数 | **无（只有 SELECT）** | 任何写 |
| 边界 | `backend/main.py`、`backend/mcp/server.py` | 路由 / 工具 | 无 | **任何 SQL、任何业务判断** |
| 契约 | `backend/schemas.py` | Pydantic | 无 | 碰 DB |

**读入口**例外说明：`service.get_tree` / `get_status` / `list_books` 是只读的，边界层可以调。
**写入口**没有例外：账本的一切变更只有 `apply_op` / `undo` / `redo` / `reset_to_m0` 四条路。

### 2.1 账本包内部的分层

| 模块 | 职责 | 能不能碰 DB |
|---|---|---|
| `errors.py` | 错误码常量 + `LedgerError`（message 是人话） | 否 |
| `amount.py` | **整数分**工具（`cents` / `money` / `net`）—— 纯代数，零 IO | 否 |
| `atoms.py` | 原子层：方向判定、退款配对、分裂适用域、腿的构造 | 否 |
| `ops.py` | 8 个纯操作 | 否 |
| `invariants.py` | I1–I6 + 审计链 + **聚合**（V3 的 `tree.py` 合并到这里） | 否 |
| `loader.py` | **唯一**的账本侧 SQL 入口（只读） | 只读 |
| `store.py` | **唯一**写 `ledger_*` 的模块；**不导出连接** | 只写 `ledger_*` |
| `service.py` | HTTP 与 MCP **共用**的读写接口 | 调 loader/store |
| `migrate.py` | 一次性迁移 CLI（`python -m backend.ledger.migrate`） | 调 service |

> **V3 的两处结构变化**：
> ① `tree.py` 已删 —— 节点/聚合并入 `invariants.py`（`aggregate()` 仍是「一条路聚合、一条路手算」的防错结构）。
> ② 金额从 `Decimal` 换成**整数分**：`amount.py` 只在 HTTP 出口做一次 `int → float`，
> 引擎内部全程整数，**浮点漂移从根上不存在**。

**纪律**：`backend/ledger/*` 只允许 `import backend.db` 和 `from backend import schemas`。
`store.py` 之外谁都不许写 `ledger_*`；`store.py` 也不许把连接交出去。

> V3 起 `service.py` 多了两条写入口：`sync_live_book()`（自动同步账本，启动时调用）
> 和 `apply_ops_batch()`（一批建议原子写入）。它们**必须落在 `store.py` 里**，
> 且每次写完照跑不变量 —— 与 `apply_op` 同等对待。

## 三、账本模型约定

### 3.1 账本（book）

- 一本账 = 用户定义的**一个阶段**：名字 + 起止日期 + 备注。
- **成员在建账时按区间冻结**：`ledger_book_tx` 是显式物化的成员集。
  理由：代数里 `X` 是**给定的**输入；冻结的 `X` 才谈得上重跑。
  新交易进来靠显式 `attach` 或新开一本账。
- **区间允许重叠**，引擎不做去重仲裁，各算各的。
- **禁止跨账汇总**：不提供 `sum_books()`。账本树与第一轮 reports **互不相加**。
- 树不跨账共享。`node_id` 自带归属前缀 `'{book_id}:n0007'`，跨账不可能撞。
- 每个请求**显式带 `book_id`**，不引入「当前账本」这个隐式状态（MCP 无会话、HTTP 多标签页会互相踩）。

### 3.2 树与腿

- 节点 `kind ∈ {root, group, external_income}`。
- **叶子 = 持腿的 group 节点**。不单独建 `kind='leaf'` 的空节点
  —— 否则 M₀ 要为每笔交易建一个节点，表会爆。与代数 §3.2 兼容。
- 节点 `op ∈ {ADD, NET}`。`NET` 只改**呈现**，不改净值。
- 腿**不物化数值**：`ledger_legs` 只存结构 `(book_id, tx_id, node_id, role)`，
  `e/i/amount` 每次读取时按当前规则实时算。
  理由：腿依赖 M，M 一改物化的数值就过期；结构（谁在哪）才需要持久化。
- `role ∈ {primary, mirror}`。**镜像腿只允许待在「外部收入节点」**（不变量 I4）。

### 3.3 口径（已定的产品决策）

| 情形 | 处理 |
|---|---|
| 支出 | 支出腿 |
| 收入 | 收入腿 |
| **中性** | **默认记支出**；例外：`item` 含「收益发放」→ 记收入 |
| 全额退款 | 原交易与退款流水均归零；退款优先于分裂（代数 §2.5/§2.6） |
| 部分退款 | 只抵扣已确认退款金额：原交易有效金额 = 原金额 − 累计退款金额；退款流水自身归零 |
| 多笔部分退款 | 按同一原交易的唯一关联退款流水累计；不重复计入收入 |
| 退款证据冲突 / 超额退款 | 不自动猜测；保留原交易金额、退款流水归零、发出警告并禁止该交易分裂 |
| 账户搬运（自有账户间划转） | 归零，**不分裂**（代数 §2.4）。⚠️ 见下方待决项 —— V3 代码用的是「按证据配对」，比这行字更严 |
| 亲情卡 / 他人代付 | 可分裂：主腿留在原处，镜像腿进外部收入节点 |

> ⚠️ 退款识别只依赖明确证据：平台累计“成功退款金额”优先；缺少该字段时，
> 使用唯一关联的退款流水合计。交易号/商家订单号必须唯一指向原交易，不能仅凭金额相同配对。
> 退款流水自身始终是零值腿；孤立退款不会被误算成收入。
>
> V3.1 对纯代数中的全额退款规则作了产品扩展：部分退款只从原交易金额中扣除已确认退款额，
> 不把整笔原交易归零。比如原消费 100、累计退款 30，最终有效支出为 70。
> 若退款累计额超过原金额，或平台累计金额与已关联退款明细冲突，系统保留警告并阻止分裂。

#### ⚠️ 待决项：账户搬运的口径（文档 vs 代码不一致）

| | 内容 |
|---|---|
| **文档承诺**（本节表格 + `02_引擎.md`） | 「自有账户间划转 → 归零，不分裂」 |
| **V3 代码实际做的** | `backend/ledger/atoms.py::_transfer_analysis`：**按证据配对** —— 共享商家订单号 + 方向相反 + 金额相等 + `tx_type` 含「转账」+ **双方都**带「本人/自有账户」证据 + 唯一配对 |
| **A 树曾经做的** | `atoms.py` 里的显式口径 `INTERNAL_FUNDINGS`（`funding='账户搬运'`）→ 判零。**这条路径在 V3 里不存在了**（全仓 `grep 账户搬运` = 0 命中），`scripts/ledger_golden_real.py` 也随之删除 |
| **后果** | A 时期已标注 `funding='账户搬运'` 的那些行，在 V3 里会从「零腿」变成**支出**（中性默认记支出） |

**二选一，需要人拍板**：
- **(a)** 把 `funding='账户搬运'` 判零加回来（`atoms.py` 加一个分支，3 行）—— 口径不变，V2 用户的既有标注继续生效；
- **(b)** 承认口径收窄，把文档这行改成「按证据配对归零（严格条件）」。

**顺带一个更细的错位**：设计文档写「**至少一条**记录明确标记本人/自有账户」，
而代码要求**双方都**标记（`atoms.py:417` 的 `_has_own_account_evidence` 逐条过滤）。
实测单侧标记 → 不配对。**不管选 (a) 还是 (b)，这句都要改** —— 现在是文档比实现松。

> 选 (b) 的话，本节的表格和 `02_引擎.md:298` 要一起改；选 (a) 的话，两处文档不用动，
> 但要补一条「`funding='账户搬运'` 的行优先于证据配对」的说明，并且
> **V2 用户那批标注怎么迁过来**（`tx_overrides.funding` 在新库里还在吗）要一并回答。

## 四、层间接口（逐条签名）

### 4.1 HTTP（8 个路由）

| 路由 | 入参 | 出参 |
|---|---|---|
| `GET /api/ledger/books` | — | `{books: [...]}` |
| `POST /api/ledger/books` | `{name, date_from, date_to}` | 整棵树（建账即 M₀） |
| `GET /api/ledger/tree` | `?book_id=&focus_node_id=` | `{root_id, nodes[], legs[], root_e, root_i, root_net}` |
| `GET /api/ledger/status` | `?book_id=` | `{invariants[], invariants_ok, placed_tx, total_tx, can_undo, can_redo, current_seq}` |
| `POST /api/ledger/op` | body `{book_id, op: <判别联合 8 分支>}` | 树 + `seq` + `warnings[]` |
| `POST /api/ledger/undo` | body `{book_id}` | 树 + `seq` |
| `POST /api/ledger/redo` | body `{book_id}` | 树 + `seq` |
| `POST /api/ledger/reset` | body `{book_id}` | 树 + `seq`（回到 M₀） |

> ⚠️ **所有 POST 端点的参数一律走 body**，不用 query。
> 混着来过一次（前端 body / 后端 query），结果「撤销 / 重做 / 回到 M₀」
> 三个按钮全坏，**而且两边都不报错** —— 后端 422，前端只弹「请求失败」。
> 现在有两条护栏盯着：
> `tests/test_ledger_http_contract.py` 用 TestClient 按前端的写法把 8 个端点调一遍；
> `test_frontend_ledger_payload_matches_backend_body` 查前端 payload 的键
> 必须是后端 body 模型的字段。

**响应体直接就是树**（不是 `{tree: ...}` 包裹）—— 前端乐观更新之后
直接用响应覆盖本地状态，少一层壳就少一处可能不一致的地方。

**为什么合成一个 `POST /api/ledger/op`**：符合「每条通道有唯一入口」；
判别联合在 OpenAPI 里是 `oneOf` + discriminator，前端 `switch (op.op)` 能穷尽检查。
每个分支 `extra="forbid"` —— 传错字段在 Pydantic 层就被拒。

### 4.2 8 个 op 分支

| `op` | 关键字段 | 语义 |
|---|---|---|
| `set_op` | `node_id, op_value` | 切节点的 ADD / NET |
| `split` | `tx_id` | 分裂：主腿留下，镜像腿进外部收入节点 |
| `unsplit` | `tx_id` | 撤销分裂 |
| `create_node` | `parent_id, name, op_value, tx_ids[]` | 新建分组并把若干 τ 挪进去 |
| `dissolve_node` | `node_id` | 解散分组，成员回到父节点 |
| `reassign` | `tx_id, to_node_id` | 改归属（**只动主腿**） |
| `attach_tx` | `tx_id, node_id?` | 把账本外的交易加进本账 |
| `detach_tx` | `tx_id` | 把交易移出本账 |

### 4.3 MCP 工具（V3.1 共 27 个）

| 工具 | 参数 |
|---|---|
| `query_ledger_books()` | — |
| `query_ledger_tree(book_id, focus_node_id?)` | — |
| `apply_ledger_op(book_id, op, ...)` | 扁平可选参数 |

V3.1 在原有报告、导入和账本工具之外增加 **14 个**分类工作流工具：

| `preview_classifications` | 保存草案并校验，零账本写入 |

| `resolve_classification_clarification` | 回写模型的澄清回答 |
| `undo_classifications` | 反向修订并停用对应规则 |
| `list_classification_rules` | 查看用户确认规则 |

| `delete_classification_rule` | 删除规则 |

**HTTP 用判别联合，MCP 用扁平可选参数**：MCP 的工具 schema 来自函数签名，
判别联合会变成 `oneOf`，模型选分支时容易出错。

**工具数量本身就是设计**：分类工具按“查询、草案、决定、规则”分组，名称直接表达下一步；
不会为每个分类标签或每种模型另建工具。

> ⚠️ **但 27 个已经在逼近那条设计红线**（原话：「AI 面对 50 个工具会懵，面对 11 个会用」）。
> 分类工具占 14 个 —— 如果真实客户端（Claude Desktop / Cursor）在选工具时开始出错，
> 第一个该砍的是**分类工作流的细分**（比如 4 个 rule CRUD 可以合成 1 个），
> 而不是账本那 3 个。**先观察，别急着砍。**

`apply_ledger_op` 的 docstring 就是 AI 的说明书：写清 8 种 op 各自需要哪些参数、
什么时候用、**别怎么用**（不要逐笔调用做批量归类；不要改金额/时间/方向；
返回值里的 `tree` 就是权威状态，不要自己维护一份树）。

### 4.4 错误语义

`LedgerError` → `main.py` 的 `@app.exception_handler(LedgerError)` → 响应体：

```json
{"code": "SPLIT_NOT_APPLICABLE", "message": "这笔交易不涉及外部额度，没法分裂。", "detail": {}}
```

- `code`：机器用，**常量集中在 `errors.py`**，不写字面量。
- `message`：**人话**。前端「抖一下 + 一句人话」和 MCP「逐笔拒绝 + 理由」共用同一份文案。
- **成功但有警告**（如「这次让总账少了 12.60」）走 `warnings: list[str]`，**不算错误**。

错误码全集见 `backend/ledger/errors.py::Code`。V3.0 将腿级校验错误码也纳入集中定义。

## 六、四道锁：AI 分类插件将来怎么被拦住

插件（基座 A）将来要写账本，**唯一的通道是 MCP 工具**。四道锁让它**结构上**写不了原始数据：

| # | 机制 | 验证方式 |
|---|---|---|
| 1 | **协议层**：插件只能通过 MCP 工具写账本；工具入参是 `LedgerOpIn` 的字段，**没有任何 SQL / 表名 / 原始字段名** | 契约测试递归扫描工具 schema，断言不含 `ledger_`/`amount`/`tx_time` 等 |
| 2 | **写路径**：插件拿不到 `sqlite3.Connection`。`store.py` 是唯一写 `ledger_*` 的模块且不导出连接 | grep + AST 护栏 |
| 3 | **原始层**：账本层没有任何 `UPDATE/DELETE transactions_raw` 的代码路径 | grep 零命中 |
| 4 | **即使写进来了也不算数**：引擎每次读树都**重算并校验不变量**，不是增量更新。外部污染了 `ledger_nodes`，下次读树 `check_all` 就会失败，状态条显示「账不平」，而不是给出一个错误的数 | 契约测试「人为造坏树 → 必须被抓到」 |

> 第 4 条是 `00_设计思路.md` §3.2「后端不会出任何错误」的技术兑现。
> **总账的数永远从叶子重算**，前端乱造也造不出错账。
