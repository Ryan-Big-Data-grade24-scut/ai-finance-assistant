## 三、🔴 两条真破线（红了，要队友修）

### 3.1 `backend/main.py` 里出现了 4 条 SQL

护栏：`test_boundary_has_no_sql[main.py]`

```
backend/main.py:82   conn.execute("SELECT COUNT(*) c FROM transactions_raw")
backend/main.py:83   conn.execute("SELECT COUNT(*) c FROM import_batches")
backend/main.py:290  conn.execute("SELECT b.*, p.name AS platform_name FROM import_batches b LEFT JOIN platforms p ...")
backend/main.py:438  conn.execute("SELECT COUNT(*) FROM transactions_raw")
```

**为什么是红线**：main.py 是**边界**，它只该做翻译。SQL 一旦出现在这里，
就等于多了一条绕过引擎的读路径 —— 第一轮口径和账本口径会在同一个函数里
悄悄合流；将来引擎口径变了（V3 已经在 `v_tx` 里接了 ledger 投影），
这些直查的地方不会跟着变，报表和星图会对不上。

**修法建议**（不归测试管，列出来给队友参考）：
- `main.py:82-83`（`/health` 存活探针）：计数不该在边界层查。
  移到 `backend/reports/` 或新建一个只读查询模块，由 main.py 调用。
- `main.py:290`（`/api/import/history`）：同上，移到 `backend/importer/` 的查询函数里。
- `main.py:438`（`/api/ai/classification/proposals`）：查 `transactions_raw` 计数，
  应改为调用 `backend/classification/service.py` 已有能力，或走 `v_tx`。
- 顺带一提：`backend/ledger/loader.py` 是**账本侧唯一的只读 SQL 入口**，
  边界层要用数据应该走它 / `ledger_service`，不该自己 `conn.execute`。

### 3.2 `backend/ledger/migrate.py` 里有一句 `print`

护栏：`test_ledger_has_no_print`

```
backend/ledger/migrate.py:11   print(json.dumps(result, ensure_ascii=False, indent=2))
```

**为什么是红线**：stdout 在 MCP 的 stdio 传输里是**协议通道**，
一句 print 就能让 MCP 会话解析失败。账本层是 MCP 工具的底座，
它必须保证「打 log 不污染 stdout」。

**修法建议**（三选一）：
1. 改用 `logging`（`logging.info(...)`）—— 推荐，日志级别可控。
2. 改用 `sys.stderr.write(...)`。
3. 把这个一次性迁移脚本挪出 `backend/ledger/`（比如 `scripts/migrate_ledger_legs.py`），
   这样账本包里就没有业务路径之外的东西了。

> 注意：`backend/ledger/migrate.py` 里的 `migrate_ledger_legs()` 本身是**正常的**——
> 它通过 `service` 走标准引擎，不违反任何护栏。要改的只是那一行 print。

## 五、HTTP 契约测试（`tests/test_ledger_http_contract.py`）

V3 的端点集与 V2 不同（账本 id 位置变了、多了一个 `/live`），所以这一份是**按 V3 重写**的，
不是照抄 A 树。3 条测试全绿。

| 测试 | 拦什么 | V3 的做法 |
|---|---|---|
| `test_all_ledger_endpoints_answer_with_frontend_shapes` | 前端按自己的写法调，某个端点的响应少一个字段 / 形状变了 → 前端运行时 undefined 崩 | 用 TestClient 依次调 `POST /books` → `GET /books` → `GET /tree` → `GET /status` → `POST /op` → `POST /undo|redo|reset` → `GET /live`（含带过滤条件的），**每个响应都按前端 TS 接口的必填字段核对**（字段集合直接从 `frontend/src/api/ledger.ts` 的 `interface LedgerTree / LedgerBook / LedgerNode / LedgerTx / LedgerLeg` 里解析出来，不是手抄的常量） |
| `test_unknown_field_in_op_is_rejected` | 前端拼错字段名 → 后端默默接受 → 写到错误的地方 | `op` 里多传一个 `oops` → 必须 400/422，且错误体的 `loc` 里要能看出**是 `oops` 这个字段**错了 |
| `test_ledger_error_shape_is_stable` | 引擎拒绝时前端要弹「人话」；错误体形状变了前端就没法解析 | 引擎自己产生的错误（`LedgerError`）响应体必须**恰好**是 `{code, message, detail}` 三键；`code` 必须登记在 `backend/ledger/errors.py::Code` 里（不许写字面量）；`message` 必须非空；`detail` 必须是对象。分别用 SPLIT_NOT_APPLICABLE（400）、BOOK_NOT_FOUND（404）、STALE_REVISION（409）三种验 |

### 一处刻意的边界划分

`{code, message, detail}` 这条只约束**引擎自己产生的错误**（`LedgerError`）。
请求体本身不合法（字段拼错、类型不对）是 FastAPI 在进引擎**之前**就拦下的，
走 `backend/main.py` 的 `RequestValidationError` 处理器，响应体是 `{"detail": [...]}`。
那是 HTTP 层的形状，不是账本的形状 —— 契约文档 §4.4 说的也是 `LedgerError` 这一路。

   main.py 的 print 不在范围内。main.py 不走 MCP stdio 通道，所以现状不算破线，

   这一句会污染 stdout。**未修，未加护栏**（加不加属于设计决策，不该测试单方面定）。

2. **`backend/mcp/server.py` 的 `EXPECTED_TOOLS` 有 27 个工具**，
   而设计文档 §4.3 写的是「V3.1 共 22 个 MCP 工具」。
   `test_ledger_tool_schema_has_no_raw_fields` 只关心账本那 3 个工具的 schema 不泄漏原始字段，
   不管工具总数，所以没红。文档与实现的数字对不上，**属于文档滞后，不是代码破线**。

4. **`db/schema.sql` 里 `ledger_placements` 还在**（264 行），

   如果要彻底封死，得给旧表加个「只有 migrate.py 能读」的更细护栏，**本次未加**。

5. **`tests/test_ledger_guardrails.py` 的 `test_boundary_has_no_sql` 只查 `backend/`**，

## 八、引擎可疑点（写黄金基线时撞见的，**只报告，未改引擎**）

| # | 现象 | 位置 | 我的判断 |

| 1 | **`ops.reconcile_special_splits` 会静默丢掉 split** —— 遇到退款/转账/证据冲突时，不报错、不告警，直接把已建的分裂抹掉 | `backend/ledger/ops.py:28` | **最该修的一个**。用户刚做的操作被静默回退，而且状态条上什么线索都没有。至少要进 `warnings` |

## 九、数据卫生护栏（`tests/test_data_hygiene_guardrails.py`，4 条）

种子内容由 `tests/tools/make_demo_seed.py` 生成（可复现）：

```bash
.venv/Scripts/python.exe tests/tools/make_demo_seed.py           # 重新生成
.venv/Scripts/python.exe tests/tools/make_demo_seed.py --check   # 只校验
```

生成脚本里有两处**必须**注意的细节：

1. **先 `PRAGMA wal_checkpoint(TRUNCATE)` 再拷贝文件**。种子是**单个文件**进 git 的；
   数据若还留在 `-wal` 里，新克隆的人装到的就是一个**空库**。
2. 账本层交给引擎自己建（`sync_live_book()`），和真实启动走**同一条路** ——
   不要手工拼 `ledger_*` 表，那样种子和引擎的语义会漂。

### 只换文件内容 ≠ 从历史里消失

把种子的内容换成虚构数据，**不等于**那个 blob 从 git 历史里消失。
这次的处理是：

1. 种子改成虚构数据（`31cde73`）；
2. 从 `62935cf` 重开一条分支 `star-v4-clean`，用一个**内容相同**的提交替换掉
   原来那个引入真实快照的提交 —— 真实 blob **从未进入 `main` 的历史**；
3. 合入 `main`（PR #12），删掉旧分支、关掉旧 PR。

⚠️ **仍然要记住**：关掉的 PR 会留下 `refs/pull/N/head`，GitHub 侧仍可能保留
旧对象。要彻底清除需要向 GitHub 提 support 请求做 GC。**所以第一道防线永远是
「提交前就别把真实数据放进去」** —— 事后清理的代价高得多。
